Authentication integration guide

Use the existing authentication widget with your configured block. This guide describes the current widget contract; availability depends on your environment and enabled providers.

1. Configure and mount the widget

  1. Create or select an authentication block in the panel and copy its reference ID. Configure login methods, provider credentials, and allowed source domains for your application.
  2. Replace both occurrences of YOUR_REFERENCE_ID with that ID. Authorization mode mounts into the element whose ID exactly matches the reference ID.
  3. Replace WIDGET_ORIGIN with the origin hosting the widget built for your API environment. The widget build produces /assets/proxy-auth/proxy-auth.js. Load it before calling window.initVerification.

The success callback is required. The example reports completion only; implement your application's private server handoff before granting access. Never log the callback result, credentials, or session tokens.

2. Establish your application session

A browser callback alone does not authorize access. Your backend must verify the authentication result using the contract for your configured block and environment, check expiry and application membership, and establish its own session. Do not assume the returned token is a JWT that your application can decode or verify locally.

Keep credentials out of URLs, logs, analytics, and support screenshots. Confirm session expiration, logout, and recovery behavior in your environment before launch.

3. Enforce membership and business permissions

Identity, authentication, application membership, and business authorization are distinct. A shared identity does not grant access to every application or organization. Your product must enforce tenant membership, resource ownership, and business permissions on every protected server request.

Authenticated widget views use the fixed mount point userProxyContainer and require an authToken. View types include user-profile, user-management, and organization-details. Enable these only for authorized users; hiding a control does not enforce a permission.

4. Verify the complete flow

  • Test on an approved source domain with the widget and API configured for the same environment.
  • Confirm the mount element exists, the script loads, and the callback runs after a real configured login.
  • Test invalid credentials, expired sessions, logout, and cross-organization access denial.
  • Use request logs to investigate API failures. Sensitive-operation activity history covers instrumented operations; it is not a complete history of every action.

For an API integration contract or environment-specific setup, contact the team. Review security boundaries before enabling access.
